# Guarded firewall migration

## Current upgrade behavior (2.0.19 / 4.0.8)

The general coordinated-update confirmation remains. A healthy managed installation already using a recognized guarded-hook source no longer needs repeated activation consent or a fresh SSH challenge for each hook update. The verified package contains FIREWALL_HOOK_BASELINES.json; release validation requires the current hook hash. Eligibility also requires a managed stable firewall version and current health. Unknown/custom/legacy source or an unhealthy baseline is not silently adopted. Disabled firewalls stay disabled.

When an eligible hook needs application, the installer revalidates automatic eligibility under the hook lock, prepares the same owned-rule/source snapshots and independent guardian, commits source and applies with the pending transaction token. Automatic confirmation requires successful family health checks before the deadline. No terminal is required for this already-adopted path. Failure or loss of the applying parent before confirmation triggers the existing independent recovery. A completed update never waits 120 seconds unnecessarily.

First legacy/custom migration retains the initial apply prompt and fresh SSH challenge described below. Deferral retains the previous hook. No-start mode does not apply rules. Future releases changing hook source must add the new current hash and retain explicitly eligible prior stable hashes in the source baseline list. Local modifications are not guessed as approved.

From package 2.0.14, use KeenTool → u to update an enabled Legacy or existing firewall. If the hook changes or health is not verified, review the guarded application prompt. The installer snapshots previous owned filter rules and runtime metadata, verifies source recovery copies, and blocks unsolicited applications of the new hook while pending. A detached guardian survives the SSH session and the monitoring service.

After the hook applies and both families match their expected enabled/disabled configuration, type the newly displayed challenge to confirm this SSH session remains reachable. The 120-second monotonic deadline starts before application. Without timely confirmation, or on apply/health failure, recovery restores previous owned rules and source files. Foreign router rules and existing set contents are preserved. This is a two-family transaction with checked recovery, not an atomic kernel commit across IPv4 and IPv6. If recovery reports an error, retain the printed private backup directory and its firewall-upgrade/guard.log for review.

A disabled firewall stays disabled. Headless runs defer application, even with --yes. An explicit installer/updater --apply-firewall still requires an interactive terminal, an existing previous hook and service startup. Plan/check never apply rules. Reattempt a deferred migration from SSH with `keentool --update --reinstall --apply-firewall` after installing the new updater; old updaters do not recognize the option.

Deferral retains the previous hook file itself, so reboot cannot silently activate the new unconfirmed hook. Package verification intentionally reports that old-hook difference until migration is completed. Other suite files can update. When a prepared/unconfirmed migration survives a reboot, the new hook first restores previous source and invokes the restored old hook; it does not blindly replay a preboot full router table. Recovery material remains private and independent of the installed helper. Automatic recovery clears the marker only after successful restoration.

The ordinary installation backup-retention choice applies after successful confirmation. A disconnected or uncatchably interrupted process can leave its recovery directory for review. Do not delete it while the marker `/opt/etc/keentool/firewall-upgrade.pending` exists or start another upgrade. For manual recovery as root, the three marker lines identify the private backup, transaction token and boot identity: invoke `/opt/bin/bash BACKUP/firewall_upgrade recover BACKUP TOKEN` using that exact record. Review errors before retrying. No username/password, statistics database, saved list or cron job is changed by the guarded rule step.

## Interrupted package 2.0.14 upgrade

` sleep: invalid number '.1' ` indicates a minimal BusyBox sleep build that rejected guardian readiness polling. It occurs before the new hook is launched. Old rollback could then stop untouched lighttpd/ulogd/vnStat services; an invalid vnStat stop command could abort before source restoration. A message that owned rules were restored does not prove source/services recovery completed.

Keep SSH open and keep the printed private recovery directory. Inspect firewall-upgrade/phase, firewall-upgrade/guard.log, the pending marker and service state. Do not reinstall over a pending transaction, remove its recovery copies or reboot as a recovery shortcut. Download recover-firewall-upgrade.sh from the 2.0.15 release, verify its SHA-256 against the published sidecar/pinned digest, then run `/opt/bin/bash ./recover-firewall-upgrade.sh EXACT-PENDING-DIRECTORY` as root after the previous installer exits.

The recovery asset verifies the matching private directory, pending marker and original recovery file hashes. It preserves the original rollback entry, replaces only that private entry atomically with the corrected service-aware version and invokes the original pinned guardian's recover action. Recovery copies are not deleted. An active maintenance owner is refused; a stale maintenance marker can be cleared after its owner is verified dead. It restores the old source installation before another update. On success check firewall_health and lighttpd/ulogd/vnstatd, then use u to install package 2.0.15. On error retain all copies and diagnose the reported service/rule failure; the tool does not claim success or guess missing historical permissions.
